## 1. Project Overview & Non-Goals

### Vision
LicensingSystem v2 must become operable from the admin panel without hidden routes, guesswork, or external log chasing. The system already has product versions, bulk key generation, notification configuration, deployment scripts, and client samples, but several features are unreachable or incomplete from the UI.

This change turns v2 into a coherent admin workflow: product versions are managed per product, new and bulk licenses select a version, SMTP test failures are observable, developer documentation and DLL downloads are available inside the admin panel, compatibility can be tested with both new and old clients, and test/demo products can be archived instead of hard-deleted.

### Current state
- `LicensingAdmin` is Blazor Server with MudBlazor.
- `LicensingApi` handles `/api/activate` and `/api/checkin` and must keep the API envelope stable.
- `LicensingCore` owns entities, EF mapping, and crypto.
- `ProductVersion` and `License.VersionId` already exist in code and production DB after `infra/migrate-v2.sql`.
- `Products.razor` only edits legacy `SoftwareProduct.CurrentVersion`; it does not manage `product_versions` rows.
- `BulkGenerate.razor` exists but is not linked from `MainLayout.razor`.
- `NotificationSettings.razor` catches SMTP failures but hides the useful exception detail.
- `ActivationHelloWorld` has `VersionId` in DTO but no operator-friendly way to test old-vs-new payload paths.
- Products are physically deleted when possible; user wants archive semantics instead.

### Target state
- Admin menu exposes all v2 modules.
- Product page lists each product's versions and supports add/rename/archive-or-delete-safe version operations according to FK constraints.
- New and bulk issuance require selecting a `ProductVersion` for existing products.
- SMTP test UI shows a sanitized diagnostic and logs detailed failure metadata server-side.
- Email send attempts for key delivery are auditable for future support.
- Admin docs page exposes latest DLL/client package links and integration docs downloads.
- Test licenses are a status/mode, not a product version; activation bypasses max-activation/review/rule enforcement only for test licenses.
- Old installers without `VersionId` remain compatible.
- Products can be archived and disappear from normal lists, dashboards, reports, and issuance pickers without deleting history.

### Users
| Persona | What they come to do | Frequency |
|---|---|---|
| SuperAdmin | Configure SMTP, manage products/versions, archive test data | Weekly |
| SupportStaff | Generate single/bulk keys, send keys/docs to developers | Daily |
| Developer integrator | Receives DLL/docs/test keys and validates activation | Per integration |
| Operator | Uses dashboard/reports without test/archive noise | Daily |

### Goals — v1 scope
1. Make every existing v2 module reachable from the admin menu.
2. Manage real `ProductVersion` rows per product and use them in license issuance.
3. Add SMTP observability and email audit foundations.
4. Add test-license mode with unlimited/rule-bypass activation semantics.
5. Add admin documentation/download portal for client DLL/API docs.
6. Add API compatibility testing for updated HelloWorld and old installer schema.
7. Replace product hard-delete UX with archive-by-default.

### Non-Goals — explicitly out of scope for v1
| Not building | Why not now | Revisit when |
|---|---|---|
| Changing `/api/activate` route, envelope, or `ResultCode` names | External clients depend on frozen contract | A formal v3 API is planned |
| Replacing MailKit or SMTP provider | Current problem is observability/configuration, not provider choice | SMTP diagnostics prove provider incompatibility |
| Full email campaign module | This slice needs transactional key delivery audit only | Marketing/bulk email is requested |
| Physical deletion of products with history | Breaks audit/report integrity | Legal retention policy permits purge |
| Rewriting deployment infrastructure | PowerShell deploy now works; only docs/status need updates | Hosting target changes |
| Multi-tenant product catalog | Current system is single-vendor | More vendors are onboarded |
| Advanced report builder | Only filtering archived/test data is needed | Custom report definitions are requested |
| New auth provider | Existing cookie/admin-role system works | SSO is required |

### Success metrics
| Metric | Target | How measured |
|---|---|---|
| v2 module reachability | 100% of v2 pages linked from menu by role | Component/pipeline tests assert links |
| Product-version issuance | Single and bulk keys require non-empty version id | Unit + component/data tests |
| SMTP diagnosability | Failed test exposes sanitized reason and logs full exception | Notification tests + log assertions |
| Compatibility | New HelloWorld and old payload activation paths pass | Automated tests and documented manual command |
| Archive behavior | Archived products vanish from normal UI/dashboard/issuance | Query tests |
| Gate | Build/test green | `dotnet build LicensingSystem.sln && dotnet test` |

**Boundary rules**
- `LicensingAdmin` never calls `LicensingApi`.
- All admin mutations write `AuditLogEntry` with `Actor = CurrentAdmin.Email(user)`.

- DB schema changes are hand-written SQL and mirrored in entities + `AppDbContext` + initial schema documentation.
- Existing `LicenseSigner.CanonicalBytes` stays unchanged unless a separate v3 signing migration is approved.

## 4. Data Model

### Delta
| Entity/Table | Change | Notes |
|---|---|---|
| `software_products` | add/use `is_archived boolean not null default false` | Hide archived products from normal lists/reports/issuance |
| `licenses` | add `Test` value to `LicenseStatus` enum conversion | Stored as varchar/int per current mapping; verify actual mapping before DDL |
| `product_versions` | manage existing rows through admin UI | Already exists from v2 migration |
| `email_log_entries` | new table for future key-send audit | Records recipient, subject/type, status, sanitized error, timestamps, license/product refs |
| `audit_log_entries` | continue for config/product/version/archive operations | Required by project rules |

### Migration contract
Create `infra/migrate-v2-admin-hardening.sql` as idempotent SQL:
- `ALTER TABLE software_products ADD COLUMN IF NOT EXISTS is_archived boolean NOT NULL DEFAULT false;`
- add `email_log_entries` only if the email audit module is implemented in this slice.
- do not store SMTP passwords or email credentials in SQL.
- include post-migration verification SELECTs.

### Test mode semantics
`LicenseStatus.Test` means:
- `/api/activate` accepts unlimited activations.
- no max activation limit.
- no review/pending requirement; activation returns approved/activated path.
- no subscription expiry enforcement.
- check-in remains successful unless license is later revoked/archived policy says otherwise.

## 6. UX Flows

1. Admin opens menu and sees Dashboard, Licenses, Generate License, Bulk Licenses, Products, SMTP, Docs, Users according to policy.
2. Admin opens Products, expands a product, adds version rows like `Free`, `Premium`, `Enterprise`.
3. Admin creates one key: selects product → version → status (`Active` or `Test`) → issues key.
4. Admin creates bulk keys: selects product → version → count → status → downloads Excel.
5. Admin configures SMTP and clicks Test: UI shows success or sanitized failure reason; logs contain full stack.
6. Admin downloads DLL/docs from Docs module and sends with test key.
7. Admin archives a test product; it disappears from normal lists/dashboard/reports but audit/history remains.
8. Developer runs new HelloWorld with `VersionId` and old installer without `VersionId`; both paths are verifiable.

## 7. Security & Privacy

- Never write SMTP passwords, PEMs, or connection strings to tracked files.
- Snackbar errors show sanitized SMTP reason only; full exception goes to server logs.
- Email audit stores metadata, not SMTP password and not private key material.
- Test mode is explicit and visible in UI/lists so it is not mistaken for production licensing.
- Archive is reversible only by authorized admin path and audited.

### 9.1 Parity and cutover
This is a schema/behavior migration, so parity is required.

1. **Parity checklist**
   - Old clients without `VersionId` activate unchanged.
   - New clients with matching `VersionId` activate.
   - New clients with wrong `VersionId` fail with `InvalidKeyFormat`.
   - Non-test licenses still obey max activations, review, revoke, expiry behavior.
   - Existing dashboard/list pages still render with archived products filtered by default.
   - Existing SMTP config can be saved without re-entering password.
2. **Parity harness**
   - `dotnet test --filter Compatibility`
   - `dotnet test --filter ActivationService`
   - manual LXC smoke: new HelloWorld mode and old installer payload against staging/test key.
3. **Coexistence**
   - New `is_archived` defaults false; existing products remain visible.
   - `LicenseStatus.Test` only affects keys explicitly issued as Test.
   - Old and new activation payloads coexist through optional `VersionId`.
4. **Cutover sequence**
   - Run migration SQL.
   - Deploy binaries with `infra/deploy.ps1`.
   - Confirm admin menu and `/admin/docs` load.
   - Issue one Test key and one Active key.
   - Run HelloWorld new mode and old payload mode.
5. **Kill criteria**
   - Any production `LicenseNotFound`/`InvalidKeyFormat` spike for old clients after deploy.
   - `licensing-admin` fails to start after migration.
   - SMTP password decryption fails for existing saved config.
6. **Decommission**
   - Remove/ignore legacy `CurrentVersion` field from UI only after ProductVersion CRUD is stable; DB column can stay for compatibility.

## 12. Release and Rollback

Release:
1. Commit each task with its checkpoint tag.
2. Run SQL migration on DB host `172.16.101.12` through LXC or admin workstation.
3. Deploy with `infra/deploy.ps1`.
4. Validate admin menu, product version CRUD, SMTP test diagnostic, one Test key, one Active key, and old-client activation.

Rollback:
- Code: reset to previous checkpoint tag and redeploy.
- DB: `is_archived` and email-log tables are additive; rollback code can ignore them.
- If test mode enum was deployed and data created, do not downgrade to code that cannot interpret `Test` without first converting or revoking those keys.

## 17. Risks

| Risk | Mitigation |
|---|---|
| Test mode weakens production enforcement accidentally | Explicit status, tests prove Active behavior unchanged |
| SMTP logs leak secrets | Log host/port/auth type/exception, never password |
| Archived products still appear in reports | Centralize list/query filters and test dashboard/report queries |
| Version CRUD allows deleting referenced version | Refuse delete/archive version when licenses reference it, or mark inactive if added |
| Old clients break | Dedicated compatibility tests before deploy |
